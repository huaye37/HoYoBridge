# 米哈游四游戏启动器可行性核查

后续真实下载试验见 [四游戏安装记录](FOUR_GAME_INSTALL_TRIAL_2026-09-05.md)。下文是此前只读可行性阶段的结论，不是当前安装状态。

日期：2026-09-05。用户将产品期望扩大为统一管理原神、崩坏 3、崩坏：星穹铁道、绝区零，并要求先核查能否实现。本轮只做现有代码与独立官方后台的验证，没有修改产品界面或实际游戏安装。

## 结论

四游戏统一下载、安装、更新、预下载管理在技术上有可行依据；已有运行中的官方后台能接受同一消息协议，以 gameBiz 区分四款游戏。不是四套完全不同的下载器。

但本轮只验证状态与安装信息查询，不证明四款游戏完整下载、差分更新、中断恢复或 Mac 运行均已可用。也没有证明官方内部接口可长期作为无界面生产 API。

## 建议实现方式

保留我们自己的 macOS 原生应用、品牌与界面，做非官方的米哈游游戏管理器；仿照官方的核心流程，不冒充官方产品，也不把用户操作转交给 Windows 启动器窗口。

1. **四游戏目录与独立状态**：同一游戏库中切换游戏，每款独立保存游戏目录、安装版本、任务状态、语音选择、预下载缓存与兼容环境；支持选择磁盘和定位已有安装。
2. **一个下载／更新协调层**：提供统一安装、暂停、继续、校验、更新、预下载和恢复操作，统一返回进度、阶段、错误码与可执行的下一步；同一目录不能有两个写入者。
3. **先验证官方后台适配**：沿用已能真实查询的官方内部消息链，继续测小范围下载、中断、续传、校验和恢复。如果能稳定控制且分发方式明确，就由我们自动准备并按需启动官方组件。CEF 调试端口仅是本地实验手段，不能直接作为发行版默认常开入口。
4. **保留下载实现的替换边界**：若官方后台无法可靠无界面控制、无法限定副作用或升级频繁破坏内部接口，则采用已有 Sophon 研究结果实现共用下载内核；不要让 UI 与私有 CefViewQuery 绑定。此分支是备选，不同时投入两套完整实现。
5. **独立的游戏运行适配**：原神保留现有成功路径，其他三款分别验证 Wine、图形后端和客户端兼容；下载已安装、校验成功、可启动、可持续游玩须分开显示。不把通用 Wine 配置标为已验证。

用户的一键流程应为：选择游戏与位置 → 自动准备依赖并安装 → 校验成功后启动。更新前发现预下载则提供预下载入口；正式更新时复用缓存并完成校验。账户与协议只在实际需要时交由用户处理，不索取或保存用户密码。

## 现有代码需要改哪里

- `GameLibrary.swift` / `GameLibraryStore.swift` 留有旧多游戏模型，但当前内建条目只有原神，不能直接把 genericCrossOverDXMT 当作其他三款的成功适配。
- `ContentView.swift` 当前直接显示 GameDetailView，没有活跃的四游戏选择流程。
- `GameInstallationService.swift` 写死 YuanShen.exe、原神空间计划和 download_genshin_cn_full.py；必须先把游戏身份、路径和任务状态拆开，再接通多游戏安装。
- `StatusStore.swift` 目前只有一个 installLocation；扩大游戏库时应迁移为每游戏位置，保留既有原神目录与用户偏好。
- `script/download_genshin_cn_full.py` 固定 hk4e、predownload=False；改一个参数不等于完成四游戏更新／预下载。

## 实施顺序与验收

第一阶段做四游戏管理模型和按游戏隔离的目录／任务状态，保留原神正常主流程；第二阶段用一个完整游戏副本打通安装／更新管理闭环，再扩展三款资源安装；第三阶段完成真实预下载窗口、跨版本合并与失败恢复；其他游戏运行兼容并行度由实际设备与实验进度决定。

“与官方功能一样”在本项目中应先落实为核心游戏管理体验：安装、识别、语音、暂停续传、更新、预下载、校验修复、路径管理和明确报错。官网资讯、账户体系、商城等不是本轮已研究或承诺实现的范围；功能对齐与四游戏 Mac 可玩性也不是同一个验收条件。

目前主要未过门槛：官方实际窗口白屏／无界面稳定控制、官方前端更新后的协议兼容、WPF 等附带操作的约束、下载与更新完整性、失败恢复、三款新增游戏的真实启动、公证与干净 Mac 安装验收。无需用户提供额外密码或先下载四款完整游戏。
