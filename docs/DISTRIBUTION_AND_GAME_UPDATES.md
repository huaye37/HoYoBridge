# 换机分发与后续游戏更新核查

核查日期：2026-09-04。这是当前代码／开发包核查，不是新电脑或 7.1 实测结论。

## 另一台 Mac

- 启动器主程序为 arm64；产品支持范围仍为 Apple Silicon、macOS 26/27。
- Wine、DXMT、Steam 兼容组件、Python 下载器、上游脚本与 Python 扩展均由打包脚本复制到应用 Resources。运行路径首先读取包内资源，而不是开发者的 LocalRuntimes。
- 主程序、Python 可执行文件和 pycurl 的依赖检查未发现必须加载开发目录的路径。扫描中 libpython 的绝对路径是该动态库自身的 LC_ID_DYLIB，不足以证明下载器依赖该开发路径；没有据此声称完成所有二进制可迁移性验证。
- 当前签名为 ad-hoc，TeamIdentifier 未设置，没有 Developer ID 分发签名／公证验收。本机 spctl 返回 accepted 的同时写明 override=security disabled，因此不能把这次 accepted 当作默认 Gatekeeper 环境下可打开的证明。
- Wine 依赖 Rosetta；当前首页没有完成 Rosetta 缺失时的一键引导闭环。
- Info.plist 的最低系统版本仍为 15.0，与产品只承诺 26/27 的范围不一致；没有全新 Mac、全新账号、默认系统安全设置下从下载到进入游戏的端到端记录。

结论：包内资源已集成，但不能对外承诺“任何符合条件的 Mac 下载即用”。正式分发前需要默认安全设置下的干净机器验收、信任链、Rosetta 引导与支持范围检查。

## 7.0 → 7.1

- 版本检测读取官方分支 tag，并非写死 7.0。应用启动后检测版本；同一安装身份的检测结果在当前进程中缓存，用户也可在更新页主动请求重新检查，并没有定时轮询新版本。
- 当前下载脚本禁用 predownload。正式版上线后才能按当前流程更新，不提供官方预下载体验。
- 更新前创建 APFS 克隆备份；备份失败则不进入下载。非 APFS 位置不能假定具备同样能力。
- 当前算法读取新版本完整文件清单：大小和 MD5 相同的文件保留；变化的文件重新下载。它不是官方 ldiff/hpatch 的完整差分更新，下载量可能明显大于官方更新包。
- 空间检查要求完整新版本安装体积加 20 GB 余量，而不是精确计算更新增量，可能过于保守。
- 当前更新仍修改原游戏目录。2026-09-05 已补持久化中断状态与启动门禁，续传保留更新前备份；取消／失败后只有记录为完整版本才可启动，否则必须继续修复或手动回滚。锁继承给下载子进程，不能在其仍写入时回滚。恢复后保留的半成品不会成为可启动反向回滚点。上述路径已用临时 APFS 文件、实际测试子进程和重建服务验收，不代表真实大版本更新、断电或网络盘恢复已经通过。
- CDN 路径前缀被固定哈希校验；官方路径变化会拒绝下载，需要发布适配后的启动器，不能静默放宽校验。
- 下载成功不等于新版本兼容。7.1 必须分别验证默认帧率启动、登录、大世界运行，以及用户可选的 120 FPS／HUD；若启动链或解帧特征变化，可能要更新启动器组件。没有任何依据保证每个游戏版本都无需适配。
- APFS 回退只是文件恢复；服务端要求新客户端时，回退到 7.0 不代表仍能联网游玩。

结论：已有版本发现、文件更新和中断恢复基础，但当前不应标成“7.1 无缝自动更新已就绪”。下一步修正更新容量预算（仍按全量保守估算），在正式更新窗口验证真实资源、回滚空间和游戏兼容；预下载仍未实现。
